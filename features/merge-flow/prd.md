# 需求 · 审批合并（子任务 → 子需求分支）

## 背景

26Q3 的工作模型：**子需求**（如"3 历史建站…"）对应一条**需求分支**（如 feature-send-receive）；
**子任务**（如 3.1.1）在自己的**开发分支**（worktree/feature-xxx）上写代码并登记初始提交。

**审批即合并**：用户点「同意」（标记通过）时，把子任务的开发分支自动合并到所属子需求的
**需求分支**（主仓库执行），并做安全判定。

## 流程

```
子任务 Review → 「标记通过」
   ① 有「有问题」的 commit？ → 拦截（先解决）
   ② 触发合并（POST /api/nodes/:id/merge）
        · 已合入（is-ancestor）→ 跳过（防重复 merge）
        · 工作区有未解决冲突（UU/AA/DD）→ 拒绝（防带冲突 merge）
        · 无可切换目标分支 → 报错
        · 正常 → git merge --no-ff（冲突则保留现场，用户终端解决后重试）
        · 全部成功 → 才真正「标记通过」
   ③ 结果弹窗（✓ 已合入跳过 / ✓ 合并 / ✗ 冲突或失败）

组/子需求级 → 「合入状态」按钮
   逐子任务列出：✓ 全部已合入 / ✗ 有未合入 + 每个仓库/分支的明细
```

## 关键约定

- **merge 执行目录**：**本地主仓库**（repos.local_path），非 worktree
- **「同意」入口**：复用「**标记通过**」（不新增按钮）
- **需求分支**：subreq 节点的属性 `reqBranch`（**必填**）
- **开发分支**：commit 登记时自动推断（`pickBranchForCommit`：排除 feature-merge、优先最具体 feature-*）

## 验收

- 已合入的分支 → 显示"已合入，跳过"（实测 1.1：3 个分支全部正确跳过）
- 未合入 → 执行合并（实测 4.1：2 仓库合并成功，mergeSha 落回执）
- 有冲突 → 弹窗提示先解决，不通过
- 组级「合入状态」→ 2/2 已合入 + 逐分支明细（实测节点 99）
